How to Use Daevon

Daevon Alpha for Windows  ·  Unreal Engine 5.4.4

This guide covers using Daevon after installation. If you haven’t installed, launched, and connected Daevon yet, start with the Quick Start.

Alpha notice

Daevon is currently alpha software. Features, commands, compatibility, and interface details may change as development continues.

What Daevon does

Daevon is a structural analysis tool for Unreal Engine projects. It reads your project, maps relationships between modules and code, and looks for places where the project’s actual structure no longer matches what it declares.

Daevon helps you find where your project stopped matching what it says it is.

In the current alpha, Daevon is observation-focused: it analyzes your project, reports what it finds, explains why an issue matters, and recommends what you can do about it. Daevon does not edit your code or project files for you — you decide what changes to make. It’s also not a general-purpose chatbot or a substitute for your own development judgment; its primary role is helping you understand the structure and health of your Unreal project.

Main features

Project analysis

Click Analyze Project near the top of the Daevon panel. Daevon scans the open project and produces a structural analysis report. Depending on your license status, the report can include the Project Health score, project statistics, findings, Why This Matters explanations, and Recommended Fix guidance.

Project Health

The Project Health score ranges from 0 to 100. A higher score indicates fewer structural issues detected by Daevon’s current rules; findings reduce the score according to their severity. The score is a quick summary — the findings contain the actionable detail. Project Health is available without an active subscription.

Project statistics

Daevon may also show a structural snapshot of the project, including modules, nodes, edges (detected dependency relationships), C++ files, header files, and finding count. These give a quick view of the size and structure Daevon detected during analysis.

Findings

Findings are the specific structural issues Daevon identifies. A finding may include severity, the affected module or relationship, evidence, Why This Matters, and a Recommended Fix. In the current alpha, because Daevon’s two active structural rules are of comparable importance, findings are typically labeled Warning; additional severity levels will appear as more rules are added. Detailed findings require an active Daevon license — without activation you can still run an analysis and view the Project Health score, and Daevon will prompt you to activate or subscribe to see the detail behind it.

Daevon chat

The chat area lets you talk to Daevon while you work. It’s a general, lightweight assistant — helpful for talking through your project or a finding — but it isn’t specialized deep Unreal expertise, and it isn’t where Daevon’s real capability lives. Daevon’s core value is in its project analysis and its commands. Treat chat as a helper on the side; treat Analyze Project and the commands as the actual tools.

What Daevon looks for

In the current alpha, Daevon’s automated analysis focuses primarily on Unreal Engine module dependency correctness. These problems are troublesome because a project may appear to work during development while still containing dependency declarations that are incomplete or incorrect. The alpha includes two main structural checks.

1. Missing module dependency

Internal rule: UE_MODULE_DEPENDENCY_MISSING

This occurs when one module uses code from another module without formally declaring that dependency — for example, DaevonTestModule using DaevonHost without declaring it. A module may compile in one environment while relying on a relationship Unreal’s build system was never told about.

Why this matters

An undeclared dependency can create fragile builds. The project may work locally but fail on another developer’s machine, after a clean rebuild, during packaging, or in another build configuration.

Typical fix

Open the affected module’s Build.cs file and declare the required module in the appropriate dependency list — PublicDependencyModuleNames or PrivateDependencyModuleNames. Use the evidence in the finding to determine which modules are involved.

2. Module boundary violation

Internal rule: UE_MODULE_BOUNDARY_VIOLATION

This occurs when a module includes a header from another module without declaring the required dependency — for example, ModuleA including ModuleB without declaring it. The code crosses an Unreal module boundary, but the build configuration doesn’t declare that relationship.

Why this matters

This creates the same class of structural risk as a missing dependency: the source relies on a relationship Unreal Build Tool doesn’t know about, which can lead to inconsistent behavior across machines, clean builds, or packaged builds.

Typical fix

Declare the required dependency in the including module’s Build.cs file.

These checks target the classic “works on my machine” category of structural problems: code that appears functional in one environment but becomes unreliable when the project is rebuilt, moved, shared, or packaged. Additional structural rules are planned for later versions.

Using Daevon commands

Daevon also supports explicit commands entered through the chat input. Commands begin with !. You don’t need these for basic project analysis — they provide direct access to additional systems such as project memory, facts, reasoning information, project selection, and the Project Knowledge Core.

Alpha note

Some of these systems are more advanced than the standard Analyze Project workflow. In the current alpha, explicit ! commands are the most reliable way to access them. Integrating these features into Daevon’s conversational chat workflow is planned for a future update.

Project memory

Project Memory lets Daevon retain approved information about a project across sessions.

!memory list                  show memory items and their state
!memory review <id>           review a proposed memory item
!memory approve <id>          approve and commit a proposed item
!memory reject <id> <reason>  reject a proposed item, with a reason
!memory edit <id> <value>     edit a memory item
!memory show <id>             display a specific memory item

Project facts

Facts let you explicitly store information Daevon should treat as known about the project.

!fact list                            list stored facts
!fact set <fact_id> <value>           create or update a fact
!fact remove <fact_id>                remove a fact
!fact set project <project_id> <fact_id> <value>   project-scoped form

Reasoning and evidence

!reason.summary    summary of Daevon's reasoning for the current conclusion
!reason.evidence   supporting evidence

Project selection

!project.select <project>   select a project as Daevon's active project
!project.current            show the currently selected project

If the named project exists, Daevon switches to it; if not, Daevon creates the corresponding project entry and selects it.

Experimental conversational project setup

Daevon also has an experimental conversational project-creation flow — you can tell it “create a new project” or “start a new project,” and it may guide you through choosing an existing or new Unreal project and its location. This workflow is experimental in the alpha and may not always behave as expected. For the more reliable flow, use !project.select <project>.

Project Knowledge Core

The Project Knowledge Core (PKC) provides a structured representation of project knowledge.

!pkc create
!pkc tree
!pkc show
!pkc link
Note on PKC availability

During the alpha, PKC commands are available in the standard command flow so early users can test them. In a future release (planned for V1), PKC is expected to move behind a paid tier. Using it now is encouraged — your usage helps test and refine it before that change.

Getting command help

If you enter a command without its required arguments, Daevon can display usage information — for example, !memory shows the expected syntax for the memory command. Additional advanced commands exist beyond those listed here; the above cover the primary user-facing systems relevant to the alpha.

Recommended workflow

  1. Run Analyze Project to establish the project’s current structural state.
  2. Review the Project Health score.
  3. Read the findings, starting with the highest-severity issues.
  4. Review Why This Matters to understand each finding’s consequence.
  5. Review the Recommended Fix.
  6. Make the appropriate project or code change yourself.
  7. Run Analyze Project again after making the change.
  8. Confirm the finding is resolved and review the updated Project Health score.
  9. Use Daevon chat if you want additional context before deciding how to proceed.

For the current module-dependency findings, resolving an issue often involves correcting the affected module’s Build.cs. Analysis itself does not modify your project, so you can rerun it whenever you want an updated structural assessment.

Understanding your Project Health score

The Project Health score gives a repeatable high-level signal of the project’s structural condition. As a general guide, a score near 100 means Daevon detected few or no issues covered by its current rules; lower scores mean more issues, more severe issues, or both.

The score is deterministic: given the same project state and the same analysis rules, Daevon produces the same score. Rerunning an unchanged project shouldn’t randomly change it. When you correct a finding and the score improves, the change reflects the updated structural analysis rather than a subjective AI judgment.

Don’t judge the project by the number alone

Project Health is a summary, not a complete assessment of project quality. A high score doesn’t mean every possible issue has been checked, and a lower score doesn’t automatically mean the project is badly designed — the score reflects the problems covered by Daevon’s current rules. For actionable information, read the findings behind the score.
